### 1.2 只要 3 条命令/请求的自证清单

> 前提：库已建（§十），后端已起（端口 10087）。这三条不需要前端、不需要 ES/RabbitMQ 也能给出结论。

```bash
# ① 真登录：拿到的必须是 HS256 JWT（三段、eyJ 开头），不是写死的字符串
curl -s -X POST http://localhost:10087/api/auth/login \
     -H "Content-Type: application/json" \
     -d '{"username":"admin","password":"Admin@123"}'

# ② 真鉴权：不带 token / 带假 token 必须 401（不是 200）
curl -s -o NUL -w "%{http_code}\n" http://localhost:10087/api/documents

# ③ 真权限：staff 账号访问管理员接口必须 403；admin 访问必须 200
#    （staff / Staff@123；接口 /api/logs 需要 sys:center）
```

三条都能对上 → 登录与鉴权链路是真的（作业《评分标准》里"假登录 -10"不成立）。
**注意 ② 的 401 是拦截器手写的响应体**（`LoginInterceptor.java:97-102`），不是 Spring Security 的默认页 —— 本项目**没有引入 `spring-security-web`**，只引了 `spring-security-crypto` 做 BCrypt（`pom.xml:57-60`），鉴权四道关卡全部是自己实现的，读起来没有框架黑盒。

## 三 请求生命周期：一次真实请求从 HTTP 到落库

> **这是老师最关心的一节**：《作业说明》注意事项第 3 条写死"登录认证鉴权必须是真实的后端链路，写死账号密码的项目会被直接识别"。
> 所以下面把链路拆到"每一环都能点开一个文件、看到一个方法、看到一行代码"。

### 3.1 全景图

```
HTTP 请求
  │
  ├─① WebMvcConfig#addInterceptors          ← 拦截器注册：/api/**（登录、登出放行）
  │      └─ LoginInterceptor#preHandle       ← 关卡①认证：解析 Bearer → 查 Redis
  │             └─ SecurityContext#set       ← 关卡②上下文：写入 ThreadLocal
  │
  ├─② PermissionAspect#check                 ← 关卡③功能权限：@RequiresPermission
  │      └─ PermissionCacheServiceImpl#permissionsOf
  │             ├─ Redis  perm:user:{id}（30 分钟）
  │             └─ DB     PermissionRepository#findEffectivePermCodes（一条 UNION SQL）
  │
  ├─③ XxxController#method                   ← 路由 / @Valid 参数校验 / 包 ResponseResult
  │
  ├─④ XxxServiceImpl#method                  ← 业务 + 关卡④归属校验（防 IDOR）+ @Transactional
  │      ├─ Repository（JpaRepository / Criteria / 原生 SQL）
  │      ├─ BaseEntity 审计列（JpaAuditConfig#auditorAware）
  │      └─ TxUtil.afterCommit(...)          ← 缓存失效 / ES 增量同步放到事务提交后
  │
  └─⑤ ResponseResult{code,message,data}      ← 统一响应体；异常走 GlobalExceptionHandler
```

### 3.2 逐环拆解（每一环都可点开核对）

| 环 | 文件:行 / 类#方法 | 这一环在做什么（读代码时看什么） |
|---|---|---|
| 启动类 | [`CampusSwapApplication.java:16-17`](backend/src/main/java/com/campusswap/CampusSwapApplication.java#L16) | `@SpringBootApplication` + `@EnableJpaAuditing(auditorAwareRef = "auditorAware")` —— 打开 JPA 审计，审计列的"操作人"才有来源 |
| ① 拦截器注册 | [`WebMvcConfig.java:44-51`](backend/src/main/java/com/campusswap/config/WebMvcConfig.java#L44) | 拦 `/api/**`；**只放行 login 与 logout**。注释里写明了为什么连 logout 也要放行（要满足"重复登出幂等返回 200"） |
| ① 认证 | [`LoginInterceptor.java:41-75`](backend/src/main/java/com/campusswap/common/security/LoginInterceptor.java#L41) | `OPTIONS` 预检直接放行（44）→ `BearerToken.parse` 取 token（48）→ **查 Redis `login:token:{token}`**（56）→ 写上下文（73） |
| ① 两个分支 | [`LoginInterceptor.java:57-63`](backend/src/main/java/com/campusswap/common/security/LoginInterceptor.java#L57) / [`:64-71`](backend/src/main/java/com/campusswap/common/security/LoginInterceptor.java#L64) | **Redis 故障 → 500**（不是 401）；**token 不在 Redis → 401**。这两条分开是实测踩坑后改的（`M4-CLOSURE.md` 缺陷 6：一次 Redis 抖动被当成"登录过期"，前端把用户集体踢回登录页） |

| ② 上下文 | [`SecurityContext.java:31`](backend/src/main/java/com/campusswap/common/security/SecurityContext.java#L31) / [`:53`](backend/src/main/java/com/campusswap/common/security/SecurityContext.java#L53) / [`:73`](backend/src/main/java/com/campusswap/common/security/SecurityContext.java#L73) | `set(userId, token)` / `requireUserId()`（拿不到就 401）/ `clear()`。Service 层靠它取"当前用户"，不必从 Controller 层层传参 |
| ③ 权限 | [`PermissionAspect.java:33-39`](backend/src/main/java/com/campusswap/common/security/PermissionAspect.java#L33) | `@Before("@annotation(requiresPermission)")`：取当前用户 → `hasPermission` → 不通过抛 `BusinessException(NO_PERMISSION)` → 全局异常处理器翻成 **403** |

### 3.4 三条旁路（比正常路径更能说明"是真链路"）

### 3.5 为什么可以断定"不是假登录"

1. **token 是算出来的，不是拼出来的**：`JwtService.java:72-82` 用 HS256 私钥签发，`verify`（`:90-107`）会校签、校签发者、校过期；篡改 payload 一位就 401（`M15-CLOSURE.md §3` 实测）。
2. **登录状态真的在 Redis**：签发时写 `login:token:{JWT} → userId` 与 `user:tokens:{userId}`（`TokenServiceImpl.java:46-53`），TTL 与 JWT 一致（2 小时，`RedisKeys.java:28`）。`redis-cli keys "login:token:*"` 能直接看到。
3. **退出真的立即失效**：`TokenServiceImpl#revoke`（`:88-97`）删键；同一个 JWT 再访问即 401，**签名本身仍然有效** —— 这正是"假登录"做不到的地方。
4. **权限来自数据库**：权限码集合由一条 SQL 从 4 张关联表合并出来，"给角色加权限 → 旧 token 立即可用；撤销 → 立即 403"（`M3-CLOSURE.md §2` US-08 实测）。

- **claims 约定**：`iss=campusswap`、`sub=userId`、`jti`（一次性随机 ID，排障可定位"具体哪次登录"）、`iat/exp`（`JwtService.java:74-81`）；密钥 <32 字节直接拒绝构造（`:57-60`）。

**关键设计（为什么这么写）**

- **消息体只放 taskId，状态以 Redis 为准**（`SearchRebuildProducer.java:35-38`）：消息小、易投递，重复投递也不会让状态错乱。
- **手动 ack 而不是自动 ack**：业务真正执行成功后才 `basicAck`，消费者中途宕机消息会重投，不会出现"消息没了但索引也没重建"。
- **失败进死信队列而不是原地重投**：`basicNack(requeue=false)` → `campusswap.search.dlx` → `campusswap.search.rebuild.dlq`（`MqConfig.java:19-32` 画了拓扑图并说明理由：索引重建失败通常是"ES 挂了/映射冲突"这类要人工介入的问题，原地 requeue 只会堵死队列并刷爆日志）。
- **幂等 + 串行锁**：任务已 `SUCCEEDED` 直接 ack 跳过（`:69-73`）；全量重建会删索引重建，同一时刻只允许一个真正在跑，用 Redis 锁（TTL 10 分钟兜底，`:40, 109-112`）。
- **broker 挂了不影响启动与其它功能**：`missing-queues-fatal: false`（`application-dev.yml:45`），提交时返回 `FAILED` + 「消息队列不可用（请确认 RabbitMQ 已启动，5672 端口可连）」。
- **Boot 4 的坑**：Spring AMQP 4 用 Jackson 3，转换器是 `JacksonJsonMessageConverter` + `tools.jackson.databind.json.JsonMapper`；课件里那种 `Jackson2JsonMessageConverter` + `com.fasterxml` 在 Boot 4 工程**编译不过**（`MqConfig.java:127-135`，`M13-CLOSURE.md §5` 缺陷 1/2）。

**怎么自证**

- `verify-m13.ps1`（静态 23 + 中间件 4 + 接口 5）：含真实队名断言。
- 单测 `SearchRebuildMqTest`（6 例：ack / DLQ-nack / 异常 / 幂等 / 未知任务 / 锁占用）+ `SearchRebuildTaskStoreTest`（4 例，真连 Redis）。
- 实测（`M13-CLOSURE.md §1`）：
  - 提交接口 **3 ms / 17 ms** 返回 `SUBMITTED` + 全局唯一 `taskId`（作业/课件要求 20ms 内）；
  - 消费者 `SUBMITTED → RUNNING → SUCCEEDED`（28 篇 / 785~1767 ms）；
  - 故意停掉 ES → 任务 `FAILED` + **DLQ 收到 1 条、主队列 0 条**（无死循环）；
  - 停掉 broker 重启应用 → **启动正常**、检索可用、提交返回 `FAILED` + 中文原因。
- 控制台自证：`http://localhost:15672`（账号 `campusswap`）能看到 2 个交换机 + 2 个队列；DLQ 有残留时用 `rabbitmqctl purge_queue campusswap.search.rebuild.dlq` 清理。

| `verify-m6.ps1` | 末行 `PASS=49 FAIL=0`，但**打印了一条 `[FAIL] A4.no-spring-context-in-new-tests`（期望 0 实得 1）且未计入计数** | **不完全一致，如实记录** |

**关于那一条 `[FAIL]` 的说明**（不改代码，只描述现象）：`verify-m6.ps1` 的 A4 断言"M6 之后新增的测试不带 Spring 上下文"，而 M13/M14/M15 之后确实新增了需要 Spring 上下文的集成测试（如 `SearchRebuildMqTest`）；同时该脚本的 `[FAIL]` 分支没有把失败计入末尾的 `FAIL` 计数，于是出现"打印失败但末行报 0 失败"的自相矛盾。
→ **两个结论**：① 机检脚本本身也会随里程碑漂移，项数与结论**以脚本自己的输出行为准**（上表的"项数"是各里程碑收口时的记录值）；② 这条不影响任何交付功能，但它恰好说明这套机检是"会失败、会喊"的，而不是摆设。

**没跑的**：`verify-m2 / verify-db-deep`（需要以 root 连库）、`verify-m3-http / m4-http / m6-http / m8 / m13 / m14 / m15`（需要后端与中间件在跑，且 HTTP 类会改数据）。它们的项数取自上表的收口记录，我**没有**把它们当成自己跑出来的结果。

## 八 编码约定红线（读代码时会遇到的"怪规矩"及其原因）

> 这一节解释"为什么代码长这样"。每条都配了**守卫它的机检断言**，所以你既可以读代码确认，也可以跑脚本确认。

|---|---|---|---|---|
| 1 | **所有接口返回 `ResponseResult{code,message,data}`** | 前端只写一套拦截逻辑（`code !== 200` 即提示） | `ResponseResult.java:12`；异常统一由 `GlobalExceptionHandler` 翻译 | `verify-api-spec.ps1` Q（code/message/data 三处计数相等） |

```bash

# ② 起后端（端口 10087；不需要装 Maven，用自带 wrapper）
cd backend && ./mvnw spring-boot:run

# ③ 起前端（端口 5173）
cd frontend && pnpm install && pnpm run dev

# ④ 浏览器打开 http://localhost:5173 ，用 admin / Admin@123 登录
```
